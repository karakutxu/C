There is one correction we would make to the above implementation before using it as the final demo: the B-side UDP receiver should be integrated into the select() loop rather than being mentioned as a separate application. That keeps the demo completely self-contained.

So we recommend this small architectural refinement.

The important part of the demo

The final data path is:

             INSTANCE A

   sendto(10.0.1.99)
          │
          ▼
   ┌───────────────┐
   │ Linux routing │
   └───────┬───────┘
           │
           │ route:
           │ 10.0.1.0/24
           │ via 192.168.0.2
           ▼
   ┌────────────────────┐
   │ Linux neighbour    │
   │ / ARP              │
   │                    │
   │ 192.168.0.2        │
   │       ↓            │
   │ 02:00:00:00:00:02 │
   └─────────┬──────────┘
             │
             ▼
           TAP0
             │
             │ complete Ethernet frame
             ▼
       proto_output()
             │
             │ eth->h_dest
             ▼
       02:00:00:00:00:02
             │
             │ MAC[5]
             ▼
       COMSYS L2 = 2
             │
             ▼
          veth0
             │
             │ veth pair
             ▼
          veth1
             │
             ▼
       proto_input()
             │
             ▼
           TAP1
             │
             ▼
       Linux IP stack
             │
             ▼
       10.0.1.99

That is the behaviour ag2 were looking for.

Why this is better than simply changing IFF_TUN to IFF_TAP

Simply doing:

ifr.ifr_flags = IFF_TAP | IFF_NO_PI;

would give you Ethernet frames, but your original build_packet() would still be constructing the packet itself.

That would not prove the important thing.

In this version, the packet is generated by:

sendto(...)

and therefore Linux has to do the normal networking work.

In particular, Linux has to resolve:

10.0.1.99
       ↓
next hop 192.168.0.2
       ↓
ARP
       ↓
02:00:00:00:00:02

Only then does the resulting Ethernet frame reach:

proto_output()

So when this code executes:

struct ethhdr *eth = (struct ethhdr *)m->data;

uint8_t l2 = eth->h_dest[5];

the value really came from the Linux neighbour/MAC selection, rather than being put there by your test code.

One more change I strongly recommend

For the cleanest demonstration of the LynxOS port, I would actually rename this:

mac_to_comsys_l2()

to something such as:

get_comsys_l2_from_mac()

and eventually make it correspond to your real ported function.

For example:

static uint8_t
get_comsys_l2_from_mac(const unsigned char *mac)
{
    /*
     * Demo mapping:
     *
     *     MAC xx:xx:xx:xx:xx:N
     *
     * maps directly to:
     *
     *     COMSYS L2 address N
     */
    return mac[5];
}

Then the correspondence with the old code becomes very obvious:

LYNXOS
------

dst->sa_data[5]
       │
       ▼
COMSYS L2 address


LINUX / TAP DEMO
----------------

eth->h_dest[5]
       │
       ▼
COMSYS L2 address

That is, in my view, the most useful thing for this particular porting demonstration: you're not trying to emulate LynxOS dst->sa_data; you're demonstrating that the information it provided to the legacy code is available at the Linux L2 boundary once the interface is changed from TUN to TAP.



REMOVE ARP ………………………………………………………………….
================================================================================================================================
this demo is not quite in line with KAKA because it relies on Linux ARP/neighbour discovery to learn:

192.168.0.2 → 02:00:00:00:00:02

If KAKA has no ARP, then that mapping must be configured explicitly. The good news is that this is actually a better match for your legacy LynxOS architecture, because the L2 address is then an explicit configuration item rather than something dynamically discovered.

What the demo should model

You effectively have:

IP destination
     │
     ▼
Linux routing
     │
     ▼
KAKA interface configuration
     │
     │ explicit mapping
     ▼
COMSYS L2 address
     │
     ▼
MAC address

with your demo's fixed relationship:

COMSYS L2 address N
        ↕
MAC xx:xx:xx:xx:xx:N

So, for example:

KAKA interface       IP              MAC                  COMSYS L2
-------------------------------------------------------------------
KAKA-A               10.0.0.99       02:00:00:00:00:01   1
KAKA-B               10.0.1.99       02:00:00:00:00:02   2
What is missing from my previous demo

The previous version had this:

Linux routing
      ↓
ARP
      ↓
destination MAC
      ↓
TAP
      ↓
proto

You don't want that.

You want:

Linux routing
      ↓
explicit KAKA L2 configuration
      ↓
destination MAC
      ↓
TAP
      ↓
proto

The key question is therefore:

How do we make Linux put an explicitly configured MAC into the Ethernet frame without using ARP?

The answer is to configure a static neighbour entry in Linux.

For example:

ip neigh replace 192.168.0.2 \
    lladdr 02:00:00:00:00:02 \
    nud permanent \
    dev tap0

This does not perform ARP.

It tells Linux:

For traffic requiring next-hop 192.168.0.2 on tap0, use MAC 02:00:00:00:00:02.

So the mapping is explicitly configured.

But there is an important distinction

I would actually make the demo distinguish three layers of configuration.

1. IP routing

For instance:

10.0.1.0/24
       ↓
next hop 192.168.0.2

configured with:

ip route add 10.0.1.0/24 via 192.168.0.2 dev tap0
2. Static L2/neighbour configuration

Then:

192.168.0.2
      ↓
02:00:00:00:00:02

configured explicitly:

ip neigh replace 192.168.0.2 \
    lladdr 02:00:00:00:00:02 \
    nud permanent \
    dev tap0
3. KAKA/COMSYS mapping

And in your protocol code:

02:00:00:00:00:02
       ↓
MAC[5]
       ↓
COMSYS L2 address 2

That gives:

                  Linux
                    │
             IP routing table
                    │
                    ▼
             next-hop IP
              192.168.0.2
                    │
                    ▼
          static neighbour entry
                    │
                    ▼
       02:00:00:00:00:02
                    │
                    ▼
                  TAP
                    │
                    ▼
             proto_output()
                    │
                    ▼
             eth->h_dest[5]
                    │
                    ▼
             KAKA L2 address
                    2

This is much closer to what you're trying to demonstrate.

Why this is particularly relevant to your LynxOS port

Your legacy code apparently gets the L2 address from:

dst->sa_data[5]

The important semantic fact is that the protocol code isn't discovering the address.

The networking layer has already selected the destination L2 address for the packet.

Your protocol then consumes that information.

In Linux, you can reproduce that semantic behaviour with:

             Linux IP stack
                   │
                   │ routing
                   ▼
             static neighbour
                   │
                   │ configured L2
                   ▼
            Ethernet frame
                   │
                   ▼
                 TAP
                   │
                   ▼
             proto_output()
                   │
                   ▼
             destination MAC
                   │
                   ▼
              COMSYS L2

So static neighbour configuration is the Linux mechanism that replaces ARP in this demonstration.

However, I would make one further change

I wouldn't call the Linux entry a "KAKA configuration" in the code, because technically Linux is still maintaining a neighbour table.

Instead, make your demo explicitly represent the KAKA configuration.

For example:

struct kaka_l2_config {
    uint32_t ip;
    unsigned char mac[ETH_ALEN];
    uint8_t comsys_l2;
};

and initialise:

static const struct kaka_l2_config kaka_peers[] =
{
    {
        .ip = ...,
        .mac = { 0x02, 0x00, 0x00, 0x00, 0x00, 0x02 },
        .comsys_l2 = 2
    }
};

Then your setup script installs the corresponding Linux static neighbour entry.

That makes the architecture explicit:

KAKA configuration
       │
       ├── IP address
       │
       ├── MAC address
       │
       └── COMSYS L2 address

rather than making it look as though KAKA somehow uses Linux ARP.

One subtle point: don't confuse MAC and COMSYS L2

From your description, there are really two concepts:

Ethernet MAC address
        ↕
fixed mapping
        ↕
KAKA/COMSYS L2 address

For this demo you have deliberately chosen:

MAC last octet == COMSYS L2 address

That's excellent for a simple demonstration.

But I would not build the real port around mac[5]. Make the mapping explicit:

uint8_t kaka_mac_to_l2(const unsigned char *mac)
{
    /* Demo-only fixed mapping */
    return mac[5];
}

Then later you can replace it with the actual KAKA addressing mechanism without changing the TAP/routing architecture.

So I would change the demo to this
ns1 / KAKA A
IP:
    10.0.0.99

KAKA peer:
    10.0.1.99
    next hop: 192.168.0.2

Explicit L2:
    02:00:00:00:00:02

COMSYS:
    L2 = 2
ns2 / KAKA B
IP:
    10.0.1.99

KAKA peer:
    10.0.0.99
    next hop: 192.168.0.1

Explicit L2:
    02:00:00:00:00:01

COMSYS:
    L2 = 1

And setup explicitly does:

ip neigh replace 192.168.0.2 \
    lladdr 02:00:00:00:00:02 \
    nud permanent \
    dev tap0

and:

ip neigh replace 192.168.0.1 \
    lladdr 02:00:00:00:00:01 \
    nud permanent \
    dev tap1

No ARP is required.

Linux will then construct:

Ethernet:

DST = 02:00:00:00:00:02
SRC = 02:00:00:00:00:01
             │
             ▼
          TAP0
             │
             ▼
       proto_output()
             │
             ▼
       eth->h_dest[5]
             │
             ▼
        KAKA L2 = 2

That is the demonstration I think you actually want.

One thing I would not do

I would not have proto_output() look up the destination MAC from its own configuration table. That would defeat the purpose of demonstrating the legacy architecture.

The point should be:

The Linux networking stack has already selected the L2 destination based on the statically configured KAKA peer information; proto receives the resulting Ethernet frame and extracts the L2 address from the destination MAC.

That is the closest Linux/TAP equivalent to your LynxOS dst->sa_data[5] behaviour.
